# Native Node.js and Python bindings

`crates/shiro-rs-node` and `crates/shiro-rs-python` are separate Cargo packages
in this repository. They call the native Rust core directly. They do not load
WebAssembly or the C ABI. The public npm and Python distribution names are
`shiro-rs`; the Python import is `shiro_rs`.

The adapters expose the existing portable computation, model, container,
serialization and training surfaces. Native host operations are included where
applicable: ciglet child-process figures and SHIRO file datasets, model files,
file alignment, and configured native/SPTK/Lua extraction. The host operations
remain synchronous and require their configured external programs when selected.
No computational implementation was removed from the Rust core.

## Ownership and types

Node uses napi-rs v3, checked JavaScript dimensions, bigint for scalar 64-bit
integers, and typed numeric arrays. Python uses PyO3 0.29, sequence inputs,
list outputs for numeric data, and bytes for encoded files. Both adapters copy
input arrays before native operations. Caller-owned mutable buffers return a
pair containing the result and updated copy. Object methods still mutate their
owner. Consuming methods invalidate their arguments; close/free are idempotent.

Callbacks retain their callable/context and propagate the original exception.
Exclusive reentry is checked. Python random/generation owners and native
figures are thread-confined; see the Python package README. Computational calls
are synchronous, so applications should schedule long work on their own workers.

Node declarations are generated by napi-rs, with explicit callback signatures.
Python distributions include .pyi files and py.typed. TypeScript consumer tests
and installed Python symbol-parity tests verify the public declarations.

## Verification

Validation ran on Windows x86_64, Rust 1.94, Node.js 24.14.1 and CPython 3.13.12.
Both adapter crates pass cargo fmt and Clippy with -D warnings.
The existing Rust, C ABI and WASM tests also run through cargo test --locked
--workspace with the new adapters included.
It covers all three native addons and extensions, original C numeric/model
fixtures, inference, training, binary model round trips, audio extraction,
callback exception identity, ownership, and native process/file operations.

Across repositories, the Node suites have 44 ciglet, 2 liblrhsmm and 20 SHIRO
reported tests. The liblrhsmm test executes its full 18-family oracle internally.
The Python suites have 30 reported tests in total. TypeScript consumer tests
cover all three packages; Python tests check installed stubs against runtime
classes and methods. liblrhsmm also compiles both adapters without the default
serialization feature.

Local npm tarballs were installed into a separate consumer directory and their
native addons loaded and computed. Wheels include type stubs, py.typed and the
GPL license. All three source distributions rebuilt into wheels outside the
original workspace through pip wheel. No npm, PyPI or crates.io publication,
GitHub release, or push was performed. Other Node/Python interpreter versions
and other platform binaries were not tested in this binding implementation.
Earlier core/C/WASM platform verification remains scoped to its existing reports.

## Reproduce

From the Node package directory:

```console
npm ci
npm run build
npm test
npm run test:types
npm pack
```

From an activated Python environment in the Python package directory:

```console
python -m pip install "maturin>=1.15,<2" pytest
maturin develop
python -m pytest tests
maturin build --release --sdist
maturin sdist
```

For all three Python suites in one invocation, use pytest's
`--import-mode=importlib` because their test modules have the same basename.
maturin build --sdist builds a wheel from the generated source distribution.
For an independent sdist verification, use `python -m pip wheel --no-deps path/to/archive.tar.gz`.
Install build-system requirements first when using --no-build-isolation.
Keep the active environment's Scripts/bin directory on PATH.

For a custom Node build directory, set CARGO_TARGET_DIR to an absolute path.
A relative napi-rs target directory can prevent declaration generation from
matching the workspace compiler's working directory. Package READMEs document
build tools, local distribution and official references.
